# Getting Started

Pinpoint Go Agent enables you to monitor Go applications using Pinpoint. This
guide takes you from `go get` to a traced request in the Pinpoint UI.

## Prerequisites

* **Go 1.25+**
* A running **Pinpoint 3.1.0+** collector, and its host address. Three ports
  must be reachable from your application: 9991 (agent), 9993 (span) and
  9992 (stat). An older collector does not take the agent's span sender.
* Linux, macOS or Windows.

Go compiles to native machine code, so there is nothing to attach at startup.
Instrumentation is a source change, which is why this guide is about code and
not about a launcher.

## How Pinpoint sees your application

The other guides use a handful of terms:

* **Application** — `ApplicationName`: the processes that run the same code.
  It is one node on the server map.
* **Agent** — one process. The agent generates its id at every start, so a
  restarted process is a new agent; `AgentName` is the label you read, and it
  defaults to `<hostname>-<pid>`.
* **Service** — `ServiceName`: a group of applications, required by the
  default agent identity ([Uid.Version](config.md#uidversion) v4).
* **Transaction** — one request, followed through every application it
  reaches. The agents pass its id downstream in `Pinpoint-*` headers.
* **Span** — the part of a transaction one process handled. A server plugin
  opens it when a request arrives and ends it with the response; a background
  job opens its own.
* **Span event** — one step inside a span: a query, an outgoing call, a block
  of code you mark. Nested span events make up the call tree.

Not every transaction is recorded. The first application a request reaches
decides whether to sample it (`Sampling.*`; by default every transaction is
recorded), and the applications after it follow that decision through the
headers. An unsampled request sends no span, but it still counts in the agent
statistics and the URL statistics below.

### What the agent sends

| Data | Sent | Shown in the Pinpoint UI |
|---|---|---|
| spans and span events of sampled requests | in batches, up to half a second after a request ends (`Collector.Grpc.SpanBatchCollectDeadline`) | server map, response time scatter chart, call tree |
| the text of each distinct SQL statement, operation name and error name | the first time it is used, and again once it has dropped out of the agent's cache | resolved into the call tree |
| agent statistics: process and system CPU, heap and stack memory, GC cycles and pause time, requests by sampling outcome, average and maximum response time, active requests by age, open file descriptors and OS threads | every 5 s (`Stat.CollectInterval`), six samples to a message (`Stat.BatchCount`) | inspector |
| URL statistics: the request count and response time histogram of each URL pattern | every 30 s, only with `Http.UrlStat.Enable` | URL statistics |
| agent information: host name, IP, pid, Go version, `ServerInfo`, and the command line unless `Collector.AgentInfo.SendArgs` is off | at registration, then every 24 h (`Collector.AgentInfo.RefreshInterval`) | server information |
| the count of active requests in real time and, when asked, the stacks of the goroutines serving them | only while someone has the real-time view open, for requests that started after it opened | real-time active request chart, active thread dump |

Go has no JVM, so the inspector's JVM-named charts carry Go values: heap is
the Go heap, non-heap the goroutine stacks, and the thread count counts OS
threads, not goroutines.

## Install
### Go get
```
go get github.com/pinpoint-apm/pinpoint-go-agent/v2
```

### import
``` go
import "github.com/pinpoint-apm/pinpoint-go-agent/v2"
```

## Create an Agent
Go programs cannot be automatically instrumented because they are compiled into native machine code.
Therefore, developers must add the codes for instrumenting to the Go program they want to track.

First, you can create a pinpoint agent from the main function or http request handler.
After you set the application name, service name, agent name, pinpoint collector's host address, and so on for ConfigOptions, 
you can call the NewAgent() function to create an agent. The agent id is generated by the agent itself;
the agent name is the stable label you choose, made of letters, digits, `.`, `_` and `-`. 
The service name is required by the default agent identity, [Uid.Version](config.md#uidversion) v4.
A Pinpoint 3.1.x collector refuses a v4 agent without an ApiKey; against one, replace `WithServiceName` with
`pinpoint.WithUidVersion("v3")`.
For more information on config option, refer the [Configuration](config.md) document.

``` go
func main() {
	opts := []pinpoint.ConfigOption{
		pinpoint.WithAppName("MyAppName"),
		pinpoint.WithServiceName("MyServiceName"),
		pinpoint.WithAgentName("my-agent"),
		pinpoint.WithCollectorHost("pinpoint's collector host"),
	}
	cfg, _ := pinpoint.NewConfig(opts...)
	agent, err := pinpoint.NewAgent(cfg)
	if err != nil {
		log.Printf("pinpoint agent start failed: %v", err) // keeps running, untraced
	}
	
	...
```

## Instrument HTTP Request

As mentioned earlier, the Go application must be manually instrumented at the source code level. 
Pinpoint Go Agent provides plugins packages to help developers trace the popular frameworks and toolkits. 
These packages help you to make instruments with simple source code modifications.
For more information on plugins packages, refer the [Plugin User Guide](plugin_guide.md).

### Inbound Http Request

The pinpoint http plugin lets you trace Go's built-in http packages.
For example, if you want to trace the handler of the http server below,

``` go
http.HandleFunc("/", index)
```
you can write code for the instruments as shown below.
``` go
http.HandleFunc("/", pphttp.WrapHandlerFunc(index))
```

The complete example code for tracing the http server's handler is as follows:
``` go
package main

import (
	"io"
	"log"
	"net/http"

	"github.com/pinpoint-apm/pinpoint-go-agent/v2"
	"github.com/pinpoint-apm/pinpoint-go-agent/plugin/http/v2"
)

func index(w http.ResponseWriter, r *http.Request) {
	io.WriteString(w, "hello world")
}

func main() {
	opts := []pinpoint.ConfigOption{
		pinpoint.WithAppName("TraceWebRequest"),
		pinpoint.WithServiceName("TraceWebRequestService"),
		pinpoint.WithAgentName("TraceWebRequestAgent"),
		pinpoint.WithCollectorHost("localhost"),
	}
	cfg, _ := pinpoint.NewConfig(opts...)
	agent, err := pinpoint.NewAgent(cfg)
	if err != nil {
		log.Printf("pinpoint agent start failed: %v", err) // keeps running, untraced
	}
	defer agent.Shutdown()                   // normal return from main
	defer pinpoint.ShutdownOnSignal(agent)() // SIGTERM/SIGINT: a defer alone does not run on a signal

	http.HandleFunc("/", pphttp.WrapHandlerFunc(index))
	...
}
```

### Outgoing Http Request 
If you are tracking outgoing HTTP requests, you must instrument the HTTP client. 
The WrapClient() function in the pinpoint http plugin allows you to trace http client calls.

``` go
func outgoing(w http.ResponseWriter, r *http.Request) {
	client := pphttp.WrapClient(nil)

	request, _ := http.NewRequest("GET", "http://localhost:9000/hello", nil)
	request = request.WithContext(r.Context())

	resp, err := client.Do(request)
	if nil != err {
		io.WriteString(w, err.Error())
		return
	}
	defer resp.Body.Close()
	io.Copy(w, resp.Body)
}

func main() {
	... //setup agent
	
	http.HandleFunc("/outgoing", pphttp.WrapHandlerFunc(outgoing))
}
```

## Instrument Web Framework
Pinpoint Go Agent provides a plugin to track the Gin, Echo, Chi and Gorilla Web framework.
Below is an example of tracking the handler of the Gin framework.
You can simply register Gin plugin with the middleware of the Gin or wrap the Gin handler like http plugin.

``` go
router.Use(ppgin.Middleware())
```
``` go
package main

import (
	"github.com/gin-gonic/gin"
	"github.com/pinpoint-apm/pinpoint-go-agent/v2"
	"github.com/pinpoint-apm/pinpoint-go-agent/plugin/gin/v2"
)

func hello(c *gin.Context) {
	c.Writer.WriteString("hello")
}

func main() {
	... //set up agent
	
	router := gin.Default()
	router.Use(ppgin.Middleware())

	router.GET("/hello", hello)
	router.Run(":8000")
}
```

## Instrument gRPC

The gRPC plugin is a set of interceptors. On a server they open the span of
each call; list them first when you chain others, so a call that a later
interceptor rejects is traced too:

```go
import "github.com/pinpoint-apm/pinpoint-go-agent/plugin/grpc/v2"

server := grpc.NewServer(
	grpc.ChainUnaryInterceptor(ppgrpc.UnaryServerInterceptor()),
	grpc.ChainStreamInterceptor(ppgrpc.StreamServerInterceptor()),
)
```

On a client they record each call as a span event and pass the transaction on
in the call's metadata:

```go
conn, err := grpc.NewClient(addr,
	grpc.WithTransportCredentials(insecure.NewCredentials()),
	grpc.WithChainUnaryInterceptor(ppgrpc.UnaryClientInterceptor()),
	grpc.WithChainStreamInterceptor(ppgrpc.StreamClientInterceptor()),
)
```

A handler's `ctx` carries the call's tracer. Pass it to the calls the handler
makes - another gRPC call, a query, an HTTP request - and they join the same
transaction:

```go
func (s *server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.User, error) {
	row := s.db.QueryRowContext(ctx, "SELECT name FROM users WHERE id = ?", req.Id)
	...
}
```

See [plugin/grpc](/plugin/grpc) for streams and a complete example.

## Instrument Database Query
Pinpoint mysql plugin is a 'database/sql' driver that instruments the go-sql-driver/mysql. 
When invoking the sql.Open() function, instead of the go-sql-driver/mysql driver,
``` go
import "database/sql"
import _ "github.com/go-sql-driver/mysql"

db, err := sql.Open("mysql", "user:password@/dbname")
```
you can use the pinpoint mysql plugin.
``` go
import _ "github.com/pinpoint-apm/pinpoint-go-agent/plugin/mysql/v2"

db, err := sql.Open("mysql-pinpoint", "root:p123@tcp(127.0.0.1:3306)/information_schema")
```

Below is a complete example of tracking MySQL calls. The pool is opened once,
in `main`, and shared by the handlers: a `sql.Open` per request leaks
connections. The query takes the request's own context, which already carries
the tracer the HTTP plugin created, so the plugin records the query under the
request's span.
``` go
package main

import (
	"database/sql"
	"fmt"
	"log"
	"net/http"

	_ "github.com/pinpoint-apm/pinpoint-go-agent/plugin/mysql/v2"
)

var db *sql.DB

func query(w http.ResponseWriter, r *http.Request) {
	var count int
	if err := db.QueryRowContext(r.Context(), "SELECT count(*) from tables").Scan(&count); err != nil {
		http.Error(w, err.Error(), http.StatusInternalServerError)
		return
	}
	fmt.Fprintln(w, "number of tables in information_schema", count)
}

func main() {
	// ... create the agent and register query with pphttp.WrapHandlerFunc, as above

	var err error
	db, err = sql.Open("mysql-pinpoint", "root:p123@tcp(127.0.0.1:3306)/information_schema")
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	// ... http.ListenAndServe
}
```

## Keep the context flowing

The agent finds the request a call belongs to through `context.Context`: a
plugin reads the tracer from the context it is given. A call made with
`context.Background()`, or with no context at all, belongs to no request and
records nothing. Two habits keep every call of a request in its trace:

* **Pass the request's context down.** Use `r.Context()` in a net/http
  handler, the handler's `ctx` in gRPC, and each framework's equivalent
  ([Getting the tracer in a handler](plugin_guide.md#getting-the-tracer-in-a-handler)),
  and hand it to the context-taking form of every call: `db.QueryContext`,
  `http.NewRequestWithContext`, `rdb.Get(ctx, key)`.
* **Give a goroutine its own tracer.** A tracer tracks one goroutine; two
  goroutines recording on one tracer corrupt its call tree. Work you hand to
  another goroutine gets a goroutine tracer, which records it under the same
  request:

  ```go
  tracer := pinpoint.FromContext(r.Context())
  f := tracer.WrapGoroutine("sendMail", func(ctx context.Context) {
      sendMail(ctx) // ctx carries the goroutine's own tracer
  }, r.Context())
  go f()
  ```

  See [Instrument Goroutine](instrument.md#instrument-goroutine).

When a call you expected is missing from a trace, a context that did not get
passed is the usual reason.

## Configure the Agent

The example above configures the agent in code, which is the shortest way to a
first trace. For anything beyond that, a config file or the environment is
better — both work without recompiling, and a config file additionally lets you
change some options on a running process.

```yaml
# pinpoint-config.yaml
applicationName: "MyAppName"
serviceName: "MyService"
collector:
  host: "collector.myhost.com"
sampling:
  type: "PERCENT"
  percentRate: 1
log:
  level: "info"
```

```go
cfg, _ := pinpoint.NewConfig(
    pinpoint.WithConfigFile("/etc/myapp/pinpoint-config.yaml"),
)
```

```bash
PINPOINT_GO_APPLICATIONNAME=MyAppName \
PINPOINT_GO_SERVICENAME=MyService \
PINPOINT_GO_COLLECTOR_HOST=collector.myhost.com \
./myapp
```

Sources are merged in this precedence order, each overriding the one below:
command flag, environment variable, config file, config function, default. See
[Configuration](config.md) for every option, and the
[examples](config.md#configuration-examples) for development, production and
container setups.

## Verify

Start your application and watch its **stdout** — that is where the agent logs
by default:

```text
INFO[...] new pinpoint agent          module=pinpoint src=agent
INFO[...] connect to collector: dns:///collector.myhost.com:9991 (ssl: false)  module=pinpoint src=grpc
INFO[...] agent registered            module=pinpoint src=agent
```

The resolved config, logged under `src=config`, comes between the first two
lines. `agent registered` means the collector accepted this agent. Then send
a request through an instrumented handler:

```bash
curl http://localhost:8000/
```

and find your `ApplicationName` in the Pinpoint UI's application list. The
transaction should appear within a few seconds.

Two things to get right from the start:

```go
agent, err := pinpoint.NewAgent(cfg)
if err != nil {
    log.Printf("pinpoint agent start failed: %v", err)  // always check this
}
defer agent.Shutdown()                                  // flush on a normal return from main
defer pinpoint.ShutdownOnSignal(agent)()                // ... and on SIGTERM/SIGINT, which a defer alone misses
```

`NewAgent()` returns a **no-op agent plus an error** when the configuration is
invalid: the application then runs perfectly and reports nothing, so the error
is your only signal. Spans are sent by a separate goroutine, so a process that
exits without `Shutdown()` drops whatever is still queued. A `defer` does not
run on a signal or `os.Exit()`; see
[Troubleshooting](troubleshooting.md#spans-missing-at-shutdown-or-on-a-rollout).

### Short-lived programs

A CLI, a batch run or a one-shot job needs one more step. `NewAgent()` returns
at once and registers with the collector in the background; until the
collector accepts the agent, every tracer is a no-op, so work that starts right
after `NewAgent()` records nothing. `Agent.Enable()` turns true once the agent
is registered. Wait for it, with a bound:

```go
agent, err := pinpoint.NewAgent(cfg)
if err != nil {
	log.Printf("pinpoint agent start failed: %v", err)
}
defer agent.Shutdown()

// A disabled or failed agent is NoopAgent(), which never becomes enabled.
if agent != pinpoint.NoopAgent() {
	for deadline := time.Now().Add(3 * time.Second); !agent.Enable() && time.Now().Before(deadline); {
		time.Sleep(20 * time.Millisecond)
	}
}
```

The plugins look the agent up on every call, so a handler can be wrapped and
`sql.Open` called before `NewAgent()`; a call made before registration passes
through untraced.

At the end, `Shutdown()` is what sends the last spans: an ended span otherwise
waits up to `Collector.Grpc.SpanBatchCollectDeadline` (500 ms) for others to
share its batch, while `Shutdown()` sends the queue at once. There is no flush
that keeps the agent running, and a runtime that freezes the process between
invocations holds whatever was queued until the process runs again.

## Before production

The defaults are chosen for a first trace. Review these before the agent goes
live:

* **Sampling.** Every transaction is recorded by default. On a busy service,
  sample a fraction with `Sampling.Type: PERCENT` and `Sampling.PercentRate`,
  and cap the peak with `Sampling.NewThroughput`
  ([Sampling policy](instrument.md#sampling-policy)).
* **Names.** Give every instance of one application the same
  `ApplicationName`. Leave `AgentName` unset, or set it per instance - in
  Kubernetes, from the pod name ([Containers](config.md#containers)) - so the
  instances can be told apart.
* **Shutdown.** Call `ShutdownOnSignal`, or `Shutdown()` from your own signal
  handler, so the last spans go out on `SIGTERM`; otherwise every rollout loses
  the last moments of each instance
  ([Spans Missing at Shutdown](troubleshooting.md#spans-missing-at-shutdown-or-on-a-rollout)).
* **What gets recorded.** SQL bind values are recorded by default
  (`SQL.TraceBindValue`), and the store plugins record keys, commands or
  queries. Read the [security notes](config.md#best-practices) and turn off
  what may carry personal data.
* **URL statistics.** Turn on `Http.UrlStat.Enable` for per-URL request counts
  and response times in the inspector. They are keyed by the route pattern, so
  register routes with patterns rather than one path per resource.
* **Collector connection.** Use TLS (`Collector.Grpc.SslEnable`) when the
  collector is reached over a network you do not trust.
* **Logs.** The agent logs to stdout at `info`. `Log.Output` sends it to a
  file instead, rotated by `Log.MaxSize` and `Log.MaxBackups`.

PINPOINT_GO_COLLECTOR_HOST=collector.myhost.com go run ./http/http_server

`example/<plugin>` (`plugin/mongomonitor`, a shared helper, has none).
